# 训练性能指标

训练性能优化首先需要回答“什么叫更快”。训练步耗时、Token 吞吐和 MFU 都能描述效率，但它们观察的对象不同：训练步耗时关注完成一次参数更新需要多久，吞吐关注单位时间处理多少数据，MFU 则把模型的有效计算量与硬件理论峰值比较。

这些指标只有在模型、数据形状、数值精度、批大小、设备数量和统计区间一致时才可比较。本章先统一各指标的定义与边界；如何构造小集群负载并从 Profile 定位瓶颈，将在下一章展开。

## 1. 统计边界：一次训练步包含什么

分布式训练中常同时出现 micro-batch、梯度累积和优化器更新。“单步耗时”必须先说明是哪一种边界：

- **micro-batch** 是一次局部前向与反向处理的数据单元；流水线并行通常在一个优化器步骤中调度多个 micro-batch。
- **优化器步骤**从上一轮参数更新结束开始，到当前轮梯度累积、梯度同步和参数更新全部完成为止。
- **测量窗口**由连续多个稳定优化器步骤组成，用于降低单步抖动对结果的影响。

本专题默认的训练步指**优化器步骤**。设测量窗口包含 $K$ 个步骤，窗口起止时间分别为 $t_{\mathrm{start}}$ 和 $t_{\mathrm{end}}$，平均训练步耗时为

$$
T_{\mathrm{step}}=
\frac{t_{\mathrm{end}}-t_{\mathrm{start}}}{K}
$$

测量窗口应避开图编译、通信器初始化、内存池扩展和数据缓存预热。异步执行框架还需要在整个窗口的起点和终点建立可靠边界；不要为了计时在每个算子或每个步骤后额外同步，否则测量动作会改变原来的并发关系。

只报告平均值也不够。同步训练的单步完成时间由最慢路径决定，因此还应记录多步分布，例如中位数（P50）、P95 和最大值，并说明是否剔除了异常步骤。

## 2. 吞吐：单位时间处理多少训练数据

吞吐是最直接的端到端性能指标。设一个优化器步骤处理的全局样本数为 $B_{\mathrm{global}}$，实际送入模型计算的 Token 数为 $N_{\mathrm{token}}^{\mathrm{processed}}$，则样本吞吐和 Token 吞吐分别为

$$
X_{\mathrm{sample}}=
\frac{B_{\mathrm{global}}}{T_{\mathrm{step}}},
\qquad
X_{\mathrm{token}}=
\frac{N_{\mathrm{token}}^{\mathrm{processed}}}{T_{\mathrm{step}}}
$$

二者的单位通常写成 samples/s 和 tokens/s。固定长度且没有 padding 的批次中，若序列长度为 $S$，则 $N_{\mathrm{token}}^{\mathrm{processed}}=B_{\mathrm{global}}S$。存在动态长度、padding、packing 或 loss mask 时，需要进一步区分：

- **处理 Token**：实际进入模型算子的 Token，反映系统承担的计算负载；padding 通常也计入这一口径。
- **有效 Token**：真正参与训练目标的非 padding、非屏蔽 Token，反映单位时间取得多少有效训练数据。

性能优化通常报告处理 Token 吞吐；评估数据效率时再补充有效 Token 吞吐。若不声明口径，改变 padding 比例就可能让 tokens/s 看似不变，但有效训练进度明显不同。

设集群有 $N_{\mathrm{device}}$ 张设备，单设备 Token 吞吐为

$$
X_{\mathrm{token/device}}=
\frac{X_{\mathrm{token}}}{N_{\mathrm{device}}}
$$

集群吞吐回答整套系统每秒处理多少 Token，单设备吞吐则更适合比较资源效率。两者必须同时带上设备数量，否则更大的集群几乎总能得到更高的集群吞吐，却不一定具有更高的扩展效率。

例如，全局批大小为 512、序列长度为 4096、平均训练步耗时为 2 秒时，集群处理 Token 吞吐为

$$
\frac{512\times4096}{2}=1{,}048{,}576\ \text{tokens/s}
$$

若使用 256 张设备，则单设备吞吐为 4096 tokens/s/device。

## 3. MFU：有效模型计算占峰值算力的比例

MFU（Model FLOPs Utilization，模型浮点运算利用率）把模型完成当前训练负载所需的理论浮点运算量，与同一时间内整个集群能够提供的理论峰值运算量比较。

设：

- $F_{\mathrm{model,step}}$ 是一个优化器步骤对应的模型理论有效 FLOPs；
- $T_{\mathrm{step}}$ 是实测训练步耗时；
- $N_{\mathrm{device}}$ 是同构设备数量；
- $P_{\mathrm{peak}}$ 是单设备在当前数值精度和计算模式下的理论峰值 FLOP/s。

则

$$
\mathrm{MFU}=
\frac{F_{\mathrm{model,step}}}
{T_{\mathrm{step}}\,N_{\mathrm{device}}\,P_{\mathrm{peak}}}
$$

分子除以训练步耗时得到模型有效 FLOP/s，分母中的 $N_{\mathrm{device}}P_{\mathrm{peak}}$ 是集群理论峰值。异构设备场景不能直接使用设备数乘单卡峰值，而应对各设备峰值求和。

### 3.1 模型 FLOPs 的统计口径

$F_{\mathrm{model,step}}$ 不是 profiler 中所有已执行指令的简单总和，而是一套预先约定的**模型有效工作量**。它可以从各算子的理论 FLOPs 精确累加，也可以用模型结构近似估算。

对稠密 decoder-only Transformer，训练前向与反向有时使用每 Token 约 $6P$ FLOPs 的粗略估计，其中 $P$ 是参与计算的参数量。这个近似把参数相关的矩阵乘作为主项，没有完整覆盖随序列长度变化的注意力计算、Embedding、归一化和其他算子，因此不能作为所有模型的固定公式。

MoE 模型还必须区分总参数与每个 Token 实际激活的专家参数。若直接把全部专家参数都放入 $6P$，会高估模型有效 FLOPs，从而得到虚高的 MFU。启用多 Token 预测、共享专家或其他附加分支时，也应把实际参与前反向的模块纳入同一套计数规则。

不同报告只有在模型 FLOPs 公式一致时才能比较。发布 MFU 时，至少应同时说明模型结构、Token 数、FLOPs 估算公式以及是否计入注意力项和附加模块。

### 3.2 硬件峰值的统计口径

$P_{\mathrm{peak}}$ 应与训练实际使用的数值精度和硬件模式一致，例如 BF16、FP16 或 FP8 的 Tensor Core 峰值。还要说明采用的是稠密峰值还是依赖结构化稀疏的峰值；模型没有使用对应稀疏模式时，不能用更高的稀疏峰值作为分母。

MFU 使用理论峰值，因此它天然低于实际可持续算力上限。不同硬件、精度或峰值口径下的 MFU 不能只看百分比直接排序。若结果超过 100%，通常意味着模型 FLOPs、设备峰值、设备数量或计时窗口至少有一项口径不一致。

### 3.3 MFU 能说明什么

MFU 适合回答：在既定模型 FLOPs 口径下，整套训练系统把多少峰值算力转化成了有效模型计算。通信等待、Host 下发、流水线气泡、低效小算子和显存带宽瓶颈都会拉长 $T_{\mathrm{step}}$，因此最终都会反映到 MFU 中。

MFU 不能直接指出瓶颈位于哪里。相同的低 MFU 既可能来自 collective 阻塞，也可能来自矩阵尺寸太小或 Device 空闲，仍需结合 Profile 分析关键路径。

## 4. MFU、HFU 与计算占比的区别

HFU（Hardware FLOPs Utilization，硬件浮点运算利用率）使用硬件实际执行的 FLOPs 作为分子：

$$
\mathrm{HFU}=
\frac{F_{\mathrm{executed,step}}}
{T_{\mathrm{step}}\,N_{\mathrm{device}}\,P_{\mathrm{peak}}}
$$

$F_{\mathrm{executed,step}}$ 包含设备实际执行的工作。Activation Checkpointing（激活重计算）会在反向阶段重新执行部分前向算子，因此可能提高 HFU 的分子，却不会增加每步处理的 Token，也不应自动增加 MFU 的模型有效 FLOPs。由此可能出现 HFU 上升、MFU 或吞吐下降的情况。

Profile 中的计算时间占比又是另一种口径。它通常描述测量窗口内有多少时间存在计算 kernel，但不关心这些 kernel 完成了多少 FLOPs，也不区分有效计算与重计算。计算和通信位于不同 stream 时还可能重叠，因此各类事件占比不能总是直接相加。

| 指标 | 分子或观察对象 | 主要用途 | 不能单独说明的内容 |
| --- | --- | --- | --- |
| MFU | 模型理论有效 FLOPs | 端到端有效算力利用 | 具体瓶颈位置 |
| HFU | 硬件实际执行 FLOPs | 设备实际算力使用 | 执行工作是否都对训练进度有效 |
| 计算时间占比 | 时间线上存在计算 kernel 的区间 | 观察空闲、通信重叠和调度 | kernel 的算力利用率与端到端吞吐 |
| 单算子利用率 | 单个 kernel 的 FLOP/s、带宽或硬件计数器 | 优化具体算子 | 该算子是否位于训练步关键路径 |

## 5. 扩展效率：增加设备后保留了多少收益

扩展效率需要先声明是强扩展还是弱扩展。

### 5.1 强扩展

强扩展保持全局工作负载不变，例如模型、全局批大小和序列长度相同，只增加设备数量。设设备数从 $N_1$ 增加到 $N_2$，训练步耗时分别为 $T_1$ 和 $T_2$，则加速比和强扩展效率为

$$
S_{\mathrm{strong}}=\frac{T_1}{T_2},
\qquad
E_{\mathrm{strong}}=
\frac{S_{\mathrm{strong}}}{N_2/N_1}
$$

随着每设备工作量变小，通信、同步和固定调度开销更难被隐藏，所以强扩展效率通常会逐步下降。

### 5.2 弱扩展

弱扩展保持每设备工作负载近似不变，并让全局批大小随设备数增加。设两个规模的集群吞吐分别为 $X_1$ 和 $X_2$，则弱扩展效率为

$$
E_{\mathrm{weak}}=
\frac{X_2/X_1}{N_2/N_1}
$$

若每设备 Token 数确实相同，也可以用 $T_1/T_2$ 表达同一效率。弱扩展衡量系统吞吐的线性度，但全局批大小变化还可能影响优化器超参数、样本效率和收敛行为，因此它不能替代相同训练目标下的总成本比较。

无论采用哪种扩展口径，都应同时报告两个集群规模、并行策略、全局与本地批大小。若扩容时还修改了 TP、PP、重计算或算子实现，得到的是两套系统配置的综合对比，不再是单一维度的扩展效率。

## 6. 显存指标：容量、峰值与不均衡

训练性能不仅受时间限制，也受每张设备的显存容量限制。至少要区分以下口径：

| 指标 | 含义 | 使用注意 |
| --- | --- | --- |
| 峰值已分配显存 | 训练张量在测量窗口内实际占用的最高值 | 记录所有 rank，并取最大值判断能否运行 |
| allocator 保留显存 | 框架内存池从设备申请并保留的空间 | 可能高于活跃张量，不能直接等同于内存泄漏 |
| 设备侧已用显存 | 驱动观察到的进程或设备总占用 | 还可能包含通信库、上下文和其他进程 |
| 显存余量 | 设备容量减去最大 rank 的峰值占用 | 需要为抖动、通信 buffer 和更长序列保留安全空间 |

只报告平均 rank 会掩盖 PP stage 或 MoE 专家负载不均。容量验收应使用所有 rank 中的峰值最大值，并标出峰值发生在前向、反向还是优化器更新阶段。

显存下降也不必然意味着性能提高。Activation Checkpointing 可以减少常驻激活，却增加重计算；参数预取可以隐藏通信，却提高短时峰值。应把峰值显存与训练步耗时放在同一组结果中比较。

## 7. 稳定性与长尾指标

大规模同步训练容易受到慢 rank、Host 抖动、网络竞争和数据形状变化影响。平均训练步耗时可能掩盖偶发但昂贵的长尾，因此建议同时报告：

- 稳定窗口内训练步耗时的 P50、P95、P99 和最大值；
- 最慢 rank 与中位 rank 的到达时间差；
- 连续多次运行的均值和离散程度；
- 异常步骤是否与 checkpoint、评估、日志或数据加载重合。

吞吐最好用“窗口内总 Token 数除以窗口总时间”计算，而不是先计算每步 tokens/s 再做简单平均。前者能让慢步骤按其真实耗时进入总体结果。

## 8. 成本与正确性指标

如果两套方案使用的设备数量不同，只比较集群吞吐不足以判断经济性。设测量窗口处理 $N_{\mathrm{token}}$ 个 Token，使用 $N_{\mathrm{device}}$ 张设备并运行 $T_{\mathrm{wall}}$ 秒，则每 Token 消耗的设备时间为

$$
C_{\mathrm{device}}=
\frac{N_{\mathrm{device}}T_{\mathrm{wall}}}{N_{\mathrm{token}}}
$$

它的单位可以写成 accelerator-seconds/token。其倒数换算后也可表示 tokens/accelerator-hour。若要比较实际费用，还需乘以对应设备、网络和主机资源的单位价格。

所有性能结果都必须带上正确性约束。更高吞吐不能来自漏算 micro-batch、减少有效 Token、跳过梯度同步或改变训练目标。至少要核对 loss、梯度范数、参数更新、有效 Token 数和数值精度；涉及算法变化时，还需要比较收敛曲线或最终任务指标。

## 9. 最小性能报告

一份能够复现和比较的训练性能报告至少应包含：

| 类别 | 需要记录的内容 |
| --- | --- |
| 硬件与软件 | 设备型号和数量、互联拓扑、关键软件版本、数值精度 |
| 模型与数据 | 模型结构、参数量、序列长度、处理与有效 Token 口径 |
| 训练配置 | 全局与本地批大小、梯度累积、并行策略、重计算配置 |
| 测量方法 | 预热步骤、统计窗口、同步边界、重复次数 |
| 时间与吞吐 | 训练步 P50/P95、samples/s、集群与单设备 tokens/s |
| 利用率 | MFU 及其 FLOPs 公式、硬件峰值口径，必要时补充 HFU |
| 容量与扩展 | 各 rank 峰值显存、强或弱扩展效率、设备时间成本 |
| 正确性 | loss、梯度、参数更新和收敛检查结果 |

训练步耗时和 Token 吞吐用于判断端到端结果，MFU 用于把有效计算映射到硬件峰值，扩展效率与设备时间成本用于判断增加资源是否值得。显存、稳定性和正确性则构成优化不可突破的边界。下一章将在这些统一口径之上，说明怎样构造性能摸底负载并从 Profile 追查瓶颈。
