# 训练性能优化

<div class="notebook-hero" markdown>

<span class="chapter-kicker">专题 · 从性能现象到可验证的优化</span>

训练性能优化不是逐个尝试算子、并行策略或配置开关，而是一个完整闭环：**固定可比较的训练负载，采集能够回答问题的数据，定位限制吞吐的关键路径，再用端到端指标验证修改是否真正有效。**

</div>

## 本专题讨论的对象

[GPU 性能基础](../gpu-basics/index.md)建立了计算、显存访问、通信和并发执行的资源视角。本专题在此基础上继续向上观察一个完整训练步，关注模型计算、优化器、数据加载和分布式通信怎样共同决定端到端性能。

开始分析前，需要先固定比较口径：模型结构、全局批大小、序列长度、数值精度、并行策略、硬件规模和统计区间都应保持一致。否则，训练步耗时或吞吐的变化可能只是工作负载改变，并不能证明优化有效。

本专题主要回答以下问题：

- 怎样建立训练性能基线，并选择训练步耗时、token 吞吐、显存峰值等验收指标。
- 怎样在采集开销与信息完整度之间取舍，避免 profiler 本身明显改变被观察的训练过程。
- 怎样把时间线中的空闲、同步和长耗时算子还原到模型计算、通信或主机调度路径。
- 怎样通过相同负载下的对照实验，确认局部改动最终改善了端到端训练效率。

## 性能优化闭环

一次可复现的性能优化通常按下面的顺序展开：

1. **确定目标**：明确优化吞吐、单步延迟、显存容量还是扩展效率，并记录不能破坏的收敛与数值正确性要求。
2. **建立基线**：固定软硬件环境和训练负载，避开编译、缓存初始化等预热阶段，记录稳定区间的数据。
3. **分层采集**：先用低开销指标确认问题稳定存在，再围绕可疑训练步采集更完整的时间线、内存和调用栈信息。
4. **定位瓶颈**：区分计算、显存访问、通信、同步和主机调度等待，找到限制关键路径的资源，而不是只挑选耗时最长的单个事件。
5. **修改并验证**：一次只改变可解释的一组因素，比较相同口径下的性能与正确性，并检查瓶颈是否转移到其他阶段。

这里的“关键路径”是决定一个训练步何时完成的依赖链。某个算子即使自身很慢，只要它完全隐藏在其他工作之后，就未必决定端到端耗时；反过来，一次很短的同步也可能让后续计算全部等待。因此，优化对象应由依赖关系和资源竞争共同确定。
